# PR #6 R1：报表导出中断后在原目录恢复

状态：**Sol 修复与自测；等待新提交 SHA 的 Terra 独立验收及小猫代码审查。** 原候选 `730bfcf6c912ceaacafa3d6dee25f06e9178ac80` 的结论是 [Terra FAIL，1 项 Major](https://github.com/handFOOLed/Stratide/pull/6#issuecomment-6465357137)，没有合并。独立验收原目录及旧提交/旧证据保持原样。

## 根因和修复

原导出器按顺序直接写最终目录。进程中断后可留下完整 `events.json` 和 0 字节 `daily.csv`；重试把这个目录当作已完成证据，因内容比较失败而退出 2。新增真实 CLI 回归在修复前复现相同错误，见 [修复前记录](evidence/m0-pr03/r1/recovery-before.txt)。本问题属于 P1 操作恢复，不修改订单、资金、风险或 v3 事件语义。

现在先把六个报表写入同级唯一暂存目录，逐文件 `sync_all` 并重新核对完整内容，再用同文件系统目录改名一次发布。最终目录出现时六份报表已经完整。若强杀发生在暂存写入期间，原目标目录仍不存在；原命令可在原路径重新导出，旧暂存副本保留。若发布已经完成，原命令只核对内容，不重复写报表。

对旧版已留下的不完整最终目录，只接受原有顺序的完整文件前缀、至多一个符合预期字节前缀的截断文件、其后缺失文件。恢复前完整归档该目录为同级 `.目录名.stratide-*.interrupted`；新结果不会原地覆盖旧部分证据。未知文件、链接、非前缀内容或不符合写入顺序的目录仍明确拒绝。归档后、发布前中断时，重试可完成目标发布，旧目录保留在归档路径。

## 复现与自测

新增测试 `interrupted_export_resumes_in_same_directory_and_preserves_partial_evidence` 从真实 CLI 基线创建完整 events/空 daily 状态，验证同一路径重试后六份报表逐字节一致、账本状态不变、部分目录完整归档。发布模块通过真实测试子进程在半文件写入、发布前、旧目录归档后和发布后 4 个断点强制退出，验证原目录恢复；故障注入只编译进测试二进制。

另外运行外部强杀脚本，直接结束生产 CLI 进程，没有启用生产故障钩子：

```powershell
./scripts/with-msvc.ps1 build -p stratide-cli --locked
python scripts/test-pr03-export-recovery.py --exe target/debug/stratide-cli.exe --output state/pr03-r1-recovery
./scripts/with-msvc.ps1 test -p stratide-cli --test replay interrupted_export_resumes --locked
```

脚本要求一个不存在的输出目录，先生成基线，再测试旧版部分报表恢复、冲突报告保留。为了稳定观察真实文件写入窗口，仅给人工数据的来源说明增加 128 KiB 测试文本，价格与规则仍是合成数据。实际第 1 次即强杀成功：暂存目录只有写入中的 `events.json`（815,187 字节），最终报表目录尚不存在；子进程退出 1。原命令原路径重试后，全部事件和六个文件与该人工输入的无中断基线一致。见[实际脚本结果](evidence/m0-pr03/r1/recovery-results.json)。冻结原样例的六个报告 SHA-256 与 `730bfcf` 及 Terra 基线完全一致，账本尾仍为 `2df95c387f82ec0399537ee7cd43e0abe06208a6c5c7aba08f1484c6ff458740`。
