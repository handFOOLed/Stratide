# M2-PR09 — 自动 EOD Operator V1

对应 [Issue #49 最新正文](https://github.com/handFOOLed/Stratide/issues/49)，基线 `main` `6e3448d15b6e5fe47678d7aec37f4cf06980fd26`（PR #48）。本分支为开发实现，交付 Draft，不合并。**Core-first / UI-later；NO_ORDERS / NO_FILLS / NO_NAV。**

## 一次配置，前台每天运行

Operator 把原采集器 → PR33 Snapshot → PR48 Shadow → 可选 PR44 Fake Auto 串起来。Owner 首次绑定已有来源并 `enable` 一次后，新的 `once/watch` 进程继续使用持久授权；无逐日许可参数，也无逐次确认。

V1 使用 Issue 允许的 **16:00 正式采集分支**：北京时间 15:15 起检查并显示 `WAITING_FOR_PUBLICATION / EARLY_SOURCE_UNVERIFIED`，16:00–17:15 之间才允许原采集器的当日自动槽。理由是原 `forward-eod-step` 将 post-16:00 `CollectionStarted` 持久化后视为当日槽已消耗，未知/失败均不自动重发；原空日线状态 `missing_daily_not_proof_of_suspension` 也没有“明确未发布、可自动重试”的协议。本 PR 保留该权威语义，未新增早期请求或有限重试，未改 1041 链、原 provider、Shadow 或 Auto 门槛。

Tushare `daily` 官方说明入库窗口为交易日 15:00–16:00，15:15 不证明已完整发布，见 [官方文档](https://tushare.pro/document/2?doc_id=27)。16:00 后返回空行仍为 `DATA_NOT_READY`，不会伪称停牌或随后自动重发。Operator 在缺少安全早期重试协议的情况下完成每日自动链路，不承诺 15:15 已取得最终日线。

## Windows 使用

Python 3.12+；从本 worktree 根目录构建原 CLI 与 Fake（MSVC 已安装）：

```powershell
pwsh -NoProfile -File scripts/with-msvc.ps1 build -p stratide-cli -p stratide-research --bins --locked --offline
```

前置条件是**已存在**的 PR33 store、原 schema-1041 observer、同来源 Shadow。Shadow 由 Owner 单独启用；Operator 不代为创建/启用它。若选择 Fake，须先按 [M2-PR07](M2_PR07.md) 创建并单独启用绑定同一 store 的 `LOCAL_FAKE_ONLY / TST` Auto。不选择 Fake 时省略 `--auto-name`，完整链路到 Shadow 即结束。候选模板仍由 [原审阅流程](M2_PR08.md) 人工选择。

以下名称和路径是占位符，替换为已有合法来源；本模块开发测试未运行这些真实采集命令：

```powershell
# 创建新的、默认 OFF 的 Operator 状态；凭据来源是固定枚举，不接受任意文件路径。
python -B scripts/eod-operator.py --snapshot-store owner-eod init `
  --observer '<已有 observer 目录>' --shadow-store owner-eod `
  --credential-source windows-credential-manager
# 可选：在 init 同时加 --auto-name '<已单独启用的 Fake Auto 名称>'

# 一次性安全配置：交互式终端内输入已有合法 Tushare Token，不回显。
python -B scripts/eod-operator.py --snapshot-store owner-eod credential

# 一次性持续授权：原 daily/trade_cal + 本地 Snapshot/Shadow/可选 Fake。
python -B scripts/eod-operator.py --snapshot-store owner-eod enable
python -B scripts/eod-operator.py --snapshot-store owner-eod watch --interval-seconds 300

# 退出后可再次运行 watch，或单次推进；没有额外 --allow... 参数。
python -B scripts/eod-operator.py --snapshot-store owner-eod once
python -B scripts/eod-operator.py --snapshot-store owner-eod status
python -B scripts/eod-operator.py --snapshot-store owner-eod history
python -B scripts/eod-operator.py --snapshot-store owner-eod verify
python -B scripts/eod-operator.py --snapshot-store owner-eod report

# 可在另一终端持久停用，不等待整个 once 的 writer lock。
python -B scripts/eod-operator.py --snapshot-store owner-eod disable
```

`disable` 阻止后续采集批次和各下游阶段；已开始的原采集请求可能完成并留下证据，停用不删除响应、不撤销已提交任务。退出 watch 用 Ctrl+C；不安装计划任务/服务，关闭、休眠或未运行期间不保证采集，不回填“准时”观察。17:15 后仍可恢复当天已采集数据的下游提交，但不会新启动错过窗口的采集。重启跨日不为过去源日重跑 Shadow/Fake。

**PR #50 P1 修复后的同步边界：** `stage_started` 只是可撤回的审计意图。每一步的最终 enabled 检查与实际 `Popen` 均处于原 Operator DB 的同一 `BEGIN IMMEDIATE` 短事务中，`disable` 写停用事件也取得这个事务。四步分别派发原 collector、Snapshot、Shadow、Auto CLI，等待和实际处理均在事务外。成功创建子进程并交给 OS 是该步已派发、不可撤销的边界；`disable` 成功返回后，直到再次显式 enable，不会再创建新的阶段子进程。先于停用派发的步骤可完成并保存原证据；停用不等待其 HTTP 或研究执行完成，但会与短暂的进程启动互斥。多进程红绿证据见 [R1](evidence/m2-pr09/r1/README.md)。

## 凭据与授权

- Windows 默认使用当前用户的原生 Credential Manager：固定 `Stratide/<Git common root hash>/tushare-daily-trade-cal-v1` Generic Credential，持久到该用户在本机的后续登录。Token 不写 Operator DB、文件、命令行、Git、日志或报告。只在创建原采集器子进程时通过原 `STRATIDE_TUSHARE_TOKEN` 环境变量交给它。
- 一次 `credential` 即可供后续新进程读取，不依赖 Owner 每日手动注入。此 API 的保护边界是 Windows 用户；同一用户运行的其他可信程序不属于独立安全沙箱。没有任意目标凭据名、任意路径或跨项目密钥读取接口。
- 已经由外层安全环境提供 Token 的场景，可在 init 明确选择 `process-env`，只读固定 `STRATIDE_TUSHARE_TOKEN`。缺失时返回 `CREDENTIAL_UNAVAILABLE`，不发请求、不消耗原自动槽；该模式的跨重启环境供应由外层负责，Windows Owner 日常使用推荐原生凭据模式。
- 真实请求同时要求 Operator 持久 enabled、原 genesis `local_automation_and_raw_storage_authorized=true`、原固定 source/genesis 绑定、合法既有接口权限及有效凭据。不会自动获得新接口、付费源、云 LLM 或订单权限。许可证与账户实际可用性继续依赖原授权，并未由本地 SHA 自证。
- `status/history/verify/report` 不读取凭据，显示 `credential_available=NOT_CHECKED_READ_ONLY`。需要删除已配置凭据时可使用 Windows 凭据管理器；停用 Operator 不等于删除凭据。

## 持久状态与恢复

```text
Git common root/state/eod-operator/<来源身份 + Operator版本的 SHA>/
  operator.sqlite        # 1090 / FULL / DELETE，append-only 审计和启停
  writer.lock            # OS 生命周期单写者，退出/强杀后释放
  collector-reports/     # 原 forward-eod-step 的原生报告，仅本地
```

状态全部 gitignored；公开查询只显示脱敏状态、源日、时间及 SHA/ref，不显示原始价格、Token、私有路径。Observer、Snapshot 与 Agent 仍使用原目录和事务。复制 observer、更名 store、改变 cwd 或从其他 worktree 启动，都不能得到新的同源 Operator 槽；同一来源的绑定别名不能接管原 writer。原 collector 槽、Shadow source-day UNIQUE 和 Auto binding/trigger 继续各自负责幂等。

每个阶段先记 `stage_started`，提交结果直接查原系统：

| 阶段 | 核对与报告 ref | 中断后行为 |
| --- | --- | --- |
| Collector | 1041 原始链/raw SHA、genesis、日历、源日、原当日 Started/Finished；journal HEAD/DB SHA | 成功则直接同步；Started/Interrupted/网络结果未知不自动重发 |
| Snapshot | PR33 原 binding/current/content SHA、最新成功 sync、原 observer DB SHA | 已发布则复用，不根据 Operator 上次 exit 推断 |
| Shadow | 原不可变 observation event ID、input/evidence SHA、真实 decision_at、原固定算法复算 | 已提交的同日观察复用；暖机不足也是真实观察状态 |
| 可选 Fake | 原 Agent intent/task/call、fake/TST 已结算结果、registration SHA 与原归档一致性 | 已完成/归档不再调用模型；缺归档走原 Auto 恢复 |
| Receipt | 源日、阶段开始记录、原子系统提交时间/ref、最终状态 | 写回前中断可从原提交恢复，不能靠 receipt 自证成功 |

`COMPLETE` 要求 observer、Snapshot、Shadow、可选 Fake 的原证据均成立且引用同一 snapshot SHA。来源修订不会让原冻结观察/任务自动改成新结果；不同快照的成功记录只能报 `PARTIAL`，不能拼接为成功。`verify/report` 还会检查历史 receipt 引用的原 journal 前缀、保留的 snapshot 内容 SHA、Shadow 和 Fake 原提交。自测是开发证据，仍需 ChatGPT 固定 HEAD 审查。

Operator 自身 receipt 事务若在写入时被强杀，下一次 `once` 在 OS writer lock 下打开原数据库，由 SQLite 恢复未提交事务，再查子系统原记录；只读查询遇到 hot journal 仅返回恢复受阻，不代为写入恢复。公开状态始终带来源 `data_mode`，synthetic fixture 不会显示成真实观察。

常见状态：

| 状态/原因 | 含义 |
| --- | --- |
| `DISABLED` | Owner 已停用，不启动新采集或下游 |
| `WAITING_FOR_CLOSE_WINDOW` | 未到北京时间 15:15 |
| `WAITING_FOR_PUBLICATION / EARLY_SOURCE_UNVERIFIED` | 15:15–15:59 自动检查，保留原 16:00 门槛 |
| `CREDENTIAL_UNAVAILABLE` | 当前进程不能取得已配置凭据，没有采集 |
| `MARKET_CLOSED` | 原 trade_cal 确认休市，不按星期推测，不运行当天研究 |
| `DATA_NOT_READY` | 原空日线或错过新采集窗口；空行不证明停牌 |
| `OUTCOME_UNKNOWN` | 原请求 Started/Interrupted/网络结果不明，不自动重发 |
| `RATE_LIMITED / PERMISSION_DENIED / SOURCE_BLOCKED / DATA_BLOCKED` | 额度/权限/日历/原始证据等未满足，不伪造有效日线 |
| `PARTIAL` | 已有上游提交，但下游关闭、失败或 ref 不一致 |
| `COMPLETE` | 当天原 EOD、Snapshot、Shadow 和配置的 Fake 均经原证据核对 |

## 开发验证与边界

命令及结果见 [m2-pr09 开发证据](evidence/m2-pr09/README.md)。新测试用本机 loopback 假 HTTP + synthetic 1041 append-only 事务、原 Snapshot/Shadow、原 Rust `cfg(test)` Fake CLI，公共行情请求和真实 LLM 调用均为 0。生产入口没有 synthetic 时钟、HTTP 地址或自定义 collector 参数。原 Rust collector 不变，其权威单槽/未知结果/日历等由原 Rust 回归覆盖；没有把测试 HTTP 适配器说成真实 Tushare 采集验收。

未验证：真实 Tushare 账户可用性、15:15 提前正式采集/NOT_READY 自动重试、长期不间断运行、Linux/macOS、物理断电和新增真实 21 日前向观察。本次没有采集真实行情，没有修改原真实 observer、历史 68/77 日证据、撮合、Risk、Ledger 或 UI。`opening_source=BLOCKED`、`historical_pit=NOT_VERIFIED`、`forward_paper_allowed=false`、`live_allowed=false` 保持。
