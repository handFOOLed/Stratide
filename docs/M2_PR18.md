## 模型与安装

先读取了官方 [TimesFM Skill](https://github.com/google-research/timesfm/blob/master/timesfm-forecasting/SKILL.md)、[system requirements](https://github.com/google-research/timesfm/blob/master/timesfm-forecasting/references/system_requirements.md)、[README](https://github.com/google-research/timesfm) 和 [2.5 模型卡](https://huggingface.co/google/timesfm-2.5-200m-pytorch)。执行了官方 `check_system.py` 的 CPU/100×512 preflight。上游 Skill 的通用“校准区间”说法不构成本项目的金融校准证据，所有尾风险/协方差仍 UNKNOWN。

- 模型：`google/timesfm-2.5-200m-pytorch`，revision `1d952420fba87f3c6dee4f240de0f1a0fbc790e3`。
- 权重：`model.safetensors`，925,181,104 bytes，SHA-256 `2f776efe6245e42b24bc4153ffdf61810140210e4bd3b01fb21f7aa779ab6ce8`。200M 是官方模型名称，固定 checkpoint 实际含 231,289,280 个参数。
- `timesfm[torch]==2.0.2` 提供 `TimesFM_2p5_200M_torch.from_pretrained`；不是模型 2.0。PyTorch 固定 `2.8.0+cpu`，其余所有传递依赖逐项固定在 [requirements.lock](../research/timesfm_cpu/requirements.lock)。Python 运行约束为 3.12，开发实际 patch 版本写入证据。
- 代码及模型卡均按 Apache-2.0 处理，见 [第三方声明](../research/timesfm_cpu/THIRD_PARTY_NOTICES.md)。完整 LICENSE/模型卡保留在本地模型目录；模型和 wheels 不入 Git。不自动升级 3.0。

推荐 Ubuntu 24.04 / Debian 12 级 cgroup v2 + systemd user manager + bubblewrap 环境；需可用 user namespaces、memory controller、`memory.peak`。首次安装是独立显式联网步骤，下载公开官方包/权重，不读取 Tushare 或 DeepSeek Token：

```bash
# 先准备 Python 3.12、venv、Rust 和 bubblewrap（由本机包管理器安装）。
bash scripts/install-timesfm-cpu.sh
cargo fetch --locked # 首次联网准备 Rust 依赖；后续运行不执行此步骤。
cargo build --workspace --locked --offline
python3.12 scripts/timesfm-cpu.py descriptor
python3.12 scripts/timesfm-cpu.py preflight
python3.12 -B scripts/test-timesfm-linux.py
python3.12 -B scripts/test-timesfm-cpu-real.py
```

安装脚本建立固定 `.venv/`，只从官方 CPU index 安装 CPU torch，再安装完整版本锁。`provision.py` 下载固定 revision 并核对硬编码官方权重 SHA；在 ignored `models/timesfm-2.5/manifest.json` 中保存模型、来源 revision、许可证、版本与四文件 SHA，不保存凭据或主机绝对路径。运行 `once/status/report/verify/preflight` 不调用安装/下载代码；Worker 强制 `HF_HUB_OFFLINE=1`、`TRANSFORMERS_OFFLINE=1`，只用固定 `/model` 本地路径及 `local_files_only=True, token=False`。缺权重或文件 SHA 错误为 `MODEL_NOT_PROVISIONED`。

## 一次运行与原任务审计

复用 PR56 已有的同一 Owner AgentDir 和绑定，不能生成第二个 Agent 费用库。若尚未绑定，用原入口显式绑定已有 Agent；不改变原预算/默认模型：

```bash
python3.12 scripts/risk-portfolio.py init --agent-dir "$EXISTING_OWNER_AGENT_DIR"
python3.12 scripts/timesfm-cpu.py enable
python3.12 scripts/timesfm-cpu.py synthetic-freeze --name cpu-example --series 4
python3.12 scripts/timesfm-cpu.py once --name cpu-example
python3.12 scripts/timesfm-cpu.py status --name cpu-example
python3.12 scripts/timesfm-cpu.py verify --name cpu-example
python3.12 scripts/timesfm-cpu.py report --name cpu-example
python3.12 scripts/timesfm-cpu.py stop
```

本地开关 `timesfm_cpu_enabled` 缺省 false，独立于旧云开关。冻结文件位于 Git common root 的 ignored `state/timesfm-cpu/<batch>/plan.json`。原 `tasks` 表分配原任务 ID，`provider_id=local-timesfm-2.5-cpu`；运行状态 `local_running` 不进入原云 Agent 的 queued/running 调度或恢复逻辑。完成/失败/取消仍进入原 task 审计。全程 `LOCAL_NO_BILLING`、零 `calls` 行，无 TST/CNY/Google 费用虚构，也不修改原 Budget。

同一 batch 的重复 `once` 复用原终态；遗留 `local_running` 在重新取得生命周期锁后标记 `WORKER_INTERRUPTED_NO_RETRY`，不会自动重跑。冻结输入、权重 manifest、Worker/Rust/CLI/依赖锁、context/batch/threads 全部绑定输入或 provider hash；改变任何一项需要新 batch/新任务。旧记录只读保留。`status/report` 只读 SQLite；`verify` 还核对本地 manifest，并通过 Rust 从保存的 Worker response 重建风险结果，不进行推理、恢复或计费。

`disable` 持久禁止后续启动/完成发布；`stop` 先 disable 再停止整个 systemd Worker unit。任务期间 Owner 暂停/disable 会使结果变为 cancelled，不能发布成功。已有 Dashboard 的云任务取消接口不扩展到本地 `local_running`；本期停止入口是上述 CLI。

## 隔离与生命周期

Worker 为按需启动、单次加载、分批预测后退出的受信 Python/PyTorch 程序。Linux 固定启动链：

```text
Owner once / original Agent lifetime lock / shared Worker lock
  → original tasks BEGIN IMMEDIATE + local enabled/paused check
  → systemd user unit stratide-timesfm-cpu.service
    MemoryMax=6 GiB / MemorySwapMax=0 / CPUQuota=200% / TasksMax=64
    RuntimeMaxSec=600 / OOMPolicy=kill / KillMode=control-group
  → bubblewrap user/pid/net/ipc/uts namespaces + drop all capabilities
    only /usr, runtime libs, read-only venv/code/model/cgroup + private /proc,/dev,/tmp
  → Python -I -B; actual memory.max/swap/oom.group and private network checked before load
  → strict JSON → Rust decode → original task completed
```

只使用固定 executable/argv，不运行模型生成的命令、URL、SQL 或代码。宿主给 Worker 的环境为 allowlist；沙箱不挂载 Owner home、AgentDir、账本或行情库。默认 2 个 OMP/MKL/Torch threads、interop 1、batch 1（可界内调至 4）、context 256（可显式到 512）、horizon 20。stdout 上限 512 KiB、输入 2 MiB，stderr 有界丢弃；Rust 桥输入另限 512 KiB。异常仅返回安全错误码，不输出 traceback、真实输入或路径。

不安装 XReg/JAX；`use_continuous_quantile_head=False`。官方 2.0.2 的模块仍加载并执行 quantile projection，ForecastConfig 没有删除该参数/head 的开关；未改上游模型或权重，也不使用其区间输出。这部分开销包含在实测内存中。`max_horizon=20` 在官方实现内部按 128 点 output patch 对齐，向外仍只返回和验证 20 个会话预测。

控制器超时/取消会 stop cgroup、kill/reap 子进程并回收管道。心跳管道每 0.5 秒更新，控制器消失/断流时 Worker 退出；600 秒系统上限是另一层有限终止。独立模型进程不进入 Rust Core。Linux 故障测试覆盖禁网络、只读模型/隐藏 home/清理环境、128 MiB 小 cgroup 的 OOM、hang/crash 与后续重启；本次 WSL2 Linux 已实测 4/4，具体宿主证据见 Linux R1；这不等于物理 N100 验收。

Windows 仅提供显式 `bench --development-cpu-diagnostic`。它有 Job Object 的 6 GiB aggregate commit/KILL_ON_JOB_CLOSE 限制和 CPU-only/offline API，但**没有 Linux 网络/文件沙箱**；生产 `once/preflight` 在 Windows 拒绝。只读 `decode-development` 可以核对真实 CPU 输出的原 RiskExpertResult 字段，但必须附 `DEVELOPMENT_ISOLATION_NOT_VERIFIED`，且不能完成生产 task。

## 原风险结果与数据语义

生产接线直接调用原 `Frozen::validate`：1–8 证券，84–192 closes，冻结日历 104–256，available_at/as_of、公司行为与原 readiness 不变。84 closes → 83 returns → 64 rolling-20 RMS。没有读取历史数据库、RAW 重解析、行情重采集或填补历史点。模型自己的 masked tensor padding 不增加任何观测或冻结交易日。

复用原 `rp::baselines` 的 Naive（最后 RMS）、EWMA（对原收益平方，λ=.94）及同一 `rolling_context`。模型预测 20 个有序索引，再映射原冻结交易日历；5/20 值是对应风险代理的均值，daily ratio、无年化。`infer_is_positive=False`，任何负值/NaN/超出 [0,.35] 的结果整批拒绝，`REJECT_NEGATIVE_NO_CLAMP / clamp_count=0`。不是收益方向、VaR/ES、尾概率或协方差预测。

保持原 RiskExpertResult V1 的 `volatility_forecast/forecast_sessions/session_mapping/market_regime/baseline_comparison` 等字段；本地 job_ref 为 null，费用为本地无计费。`RESEARCH_ONLY / ELIGIBILITY_DENIED / paper_allowed=false / can_execute_forward_paper=false / live_allowed=false`。任何真实输入仍被原 `REAL_READINESS_BLOCKED` 拒绝，旧已曝光 V1/V2 不能转换成新 forward evidence。

已读取已安装的官方 `tushare` 1.1.12 与 `tushare-data` 1.1.16 Skills，并核对官方 [daily 文档](https://tushare.pro/document/2?doc_id=27)：日线为未复权价格，盘后提供不等于历史 PIT/公司行为已核实。本模块只使用已有 `close_fen` 契约，分/元同时缩放在 close-to-close 比率中抵消；不调用 Tushare、不读 Token，也不新增供应商外发许可。

## 性能和数值对照

```bash
# Linux 受限 Worker：16 个矩阵点；每点独立冷启动，加载后运行三次相同批次。
python3.12 -B scripts/timesfm-cpu.py bench > cpu-benchmark.json
# Windows 开发诊断；不能代替 Linux/N100 验收。
python -X utf8 -B scripts/timesfm-cpu.py bench --development-cpu-diagnostic > cpu-development.json
```

10/30/50/100 × 64/128/256/512 全部是合成 RMS 输入，直接 Worker，不放宽 Frozen。记录冷加载、首批、热批次每序列 p50/p95/mean、进程 wall/CPU、峰值 RSS、整个 Job/cgroup 资源、失败数、CPU/核心/线程/内存/系统/依赖/权重 SHA/batch/context。三次输出必须一致。

另用 84/104/124 合成 closes 前缀做 sequential as-of walk-forward：每折通过原 Frozen/baselines，20 个未来目标留在宿主评价器，绝不进入 Worker。对照同目标的 MAE/RMSE、5/20 均值误差、失败/缺失数，保留模型较差或失败的结果。该对照是 synthetic 工程证据，不是独立 holdout 或真实 alpha。

所有当前开发硬件结果均标 `DEVELOPMENT_CPU_BENCHMARK`。无实际 N100 时，`N100_ACCEPTANCE=NOT_VERIFIED`；不能外推延迟 SLA。WSL2 Linux 隔离已实测，N100 与最新固定 HEAD 独立复审仍未完成。后续只需在目标机器重复同一离线脚本，无需重跑旧全市场五年数据。PR19 才处理本地风险 → DeepSeek Fusion，本期不触发任何云路径。
