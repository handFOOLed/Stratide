# ADR-004：可配置的条件自动恢复（技术故障冻结）

- 状态：**已接受（Accepted）**
- 日期：2026-10-27
- 决策范围：ADR-003 的券商订单不确定/连接故障后，恢复**账户新增风险权限**的授权政策
- 非本 ADR：券商接口的具体查询协议与退避间隔、亏损熔断解除机制

## 背景与目标

Stratide 最终希望在个人低功耗主机上无人值守运行。对每一次已明确恢复的技术故障要求人工确认会影响自动化价值；但若券商接口持续超时，盲目恢复会反复生成不确定订单并可能造成资金损失。

Owner 选择：**C — 条件自动恢复，并保留可配置选项。**

## 决策

1. **默认：`conditional_auto`。** 技术性账户冻结只有在（a）券商连接/查询已稳定、（b）原未知订单状态已通过可信渠道核实、（c）订单/成交/现金/可用资金/持仓完成全账户对账、（d）没有其他活动中的交易禁令或风控熔断、（e）故障频率未触发反复故障锁定时，才能自动解除。恢复前原有交易信号必须重新校验时效、策略状态和风控；不能自动补发旧单。
2. **可配置：`manual`。** 满足相同的技术与全账户对账前提后，仍需 Owner 使用受认证的本地管理入口明确批准，才解除技术性冻结。人工确认也不能跳过对账或解除亏损熔断。
3. **重复故障升级。** 短时间反复提交超时、对账失败、状态不一致或恢复后迅速再次故障，应转为需人工干预的 `OPERATOR_LOCKED`，不再自动恢复。频率窗口/阈值和稳定性判据在券商接入阶段按适配器能力选定，不在 M0 凭空写死具体秒数。
4. **配置边界。** Owner 可以修改技术性恢复模式及允许的稳定性/重复故障参数，但必须通过可信本地管理接口修改，变更持久化并留有审计记录；Agent、策略或远程研究 Worker 不可修改。配置选项不得禁用独立风险检查、强制对账或自动解除亏损熔断。
5. **区分禁令来源。** `BROKER_UNCERTAINTY`、`CONNECTIVITY` 等技术暂停可按本 ADR 恢复；`LOSS_CIRCUIT_BREAKER`、`DRAWDOWN_HALT` 以及其他风控锁定不得因网络恢复而自动释放。**Owner 主动接管**是另一种持久的执行权锁定：[ADR-029](0029-owner-manual-takeover-explicit-return.md) 要求 Owner 认证后明确交还，不能通过此处 `conditional_auto` 自动清除。
6. **持久化与告警。** 冻结原因、恢复模式、最近故障证据、对账完成状态和最终解锁事件应持久化；进程重启不重置尚未满足恢复条件的锁定。恢复或升级为人工锁定时记录并通知 Owner。
7. **Fail-closed for entries.** 若数据不齐全、查询失败或任一恢复条件无法确认，继续拒绝新增风险。对既有持仓的安全管理按 ADR-003 执行，不做盲目清仓。

## 最小配置表（概念，不是已实现接口）

| 名称 | 类型 | 说明 |
| --- | --- | --- |
| `recovery.mode` | `conditional_auto` / `manual` | 默认 `conditional_auto` |
| `recovery.stability_policy` | 待确定 | 按真实券商健康探测能力制定，不能靠一次成功响应认定稳定 |
| `recovery.repeat_fault_policy` | 待确定 | 反复故障触发人工锁定；不预设不切实际的阈值 |

不要为三个字段生成多余的 UI 滑块。CLI/未来控制台可用简洁选项完成操作。

## 财务风险测试（相关阶段实现）

1. 单次提交超时、随后账户查询恢复且完成对账、无其他禁令：`conditional_auto` 可解冻，但原订单不能盲目重发。
2. 相同场景 + `manual`：对账成功仍保持冻结，直到授权确认。
3. 多次故障 / 状态冲突：`conditional_auto` 不再自动解冻，进入人工锁定。
4. 同时存在亏损熔断：即使网络恢复并对账成功，仍不得新增风险。
5. 未完成对账或重启后恢复条件不足：保持冻结。

此 ADR 仅是设计决定，不声称 M0 已实现技术恢复或券商适配。
