# ADR-017：单实例交易执行与持久化安全恢复

- 状态：**已接受（Accepted）**
- 日期：2026-10-27
- Owner 选择：**方案 A — 单实例运行 + 持久化恢复**，而不是双机主备自动接管
- 范围：`stratided` 交易执行权、断电/重启恢复、跨 Windows/Mac mini/Linux 主机迁移
- 暂未决定：实际券商的接管/登录限制、备份频率及位置、存储事务细节、具体恢复核对协议与健康检测指标

## 背景

个人低频量化系统更需要保证资金/持仓准确和不发生重复真实下单，而不是为极短的停机时间构建复杂双机热备。如果两台机器同时相信自己拥有下单权限，可能产生重复订单或越过单账户风险敞口。

## 决策

1. **唯一执行主体：** 同一实际券商账户同一时间只允许一个可信核心实例拥有**真实订单提交资格**。不建设双活交易、自动备机抢占、分布式主从协调或高可用集群。开发、研究和只读监控进程不因存在而取得下单权限。
2. **防止重复运行：** 同一台主机必须使用可信进程锁或等效排他机制阻止两个交易核心同时取得执行资格。**本地进程锁不能防止另一台机器同时下单**；跨主机迁移应先明确停止/撤销旧主机执行资格，确认旧主机不会恢复下单，再赋予新主机执行权；不能把简单的数据库锁或复制目录当作跨主机互斥的保证。
3. **持久化权威状态：** 在每次可能影响资金/下单结果的动作之前或事务中记录必要的订单意图、外部请求关联 ID、提交状态、成交/撤单事件、现金/仓位账本、熔断/停机、Owner 授权与禁令。状态在故障后可重放/核对，避免“数据库说没下过单，券商其实收到了”的盲目重发。具体存储事务策略随后实现。
4. **重启默认不盲目增仓：** 启动首先加载并校验持久化状态，重建风险/订单状态，检查数据有效性、策略版本和信号时效；**真实交易恢复前**还要向券商取得可信订单、成交、可用资金、持仓和撤单状态并完整对账。遇到失配或订单未知时遵守 [ADR-003](0003-account-wide-order-uncertainty.md) 冻结全账户新风险。
5. **恢复解除规则沿用 ADR-004：** 完成权威对账、网络恢复和无其他冻结之后，按 Owner 的 `conditional_auto`（默认）或 `manual` 配置解除**技术性**暂停。重启/恢复不能自动解除亏损/回撤熔断，也不能绕过实盘启用授权。
6. **不自动清仓、不重放旧指令：** 恢复失败或状态不明时不默认强制卖出，不重复发送可能已经执行的订单；重启后仅依据最新有效账户状态和新鲜信号重新产生决策。已有仓位仍需安全监控/风险处置，但能否平仓取决于实际交易规则与已知状态。
7. **备份与迁移：** 在随后实施阶段提供简单的权威状态备份和可校验恢复流程（包含数据库一致性、配置/授权、审计和必要的策略工件引用），恢复时不依赖遗漏的 WAL 文件或随意复制正在写入的数据库。备份和恢复的机密信息须保护。迁移新主机执行权必须满足第 2、4、5 项，且券商适配器 OS 兼容性需要单独验证。
8. **明确可用性取舍：** 原主机彻底离线时，交易会暂停；不能保证始终在线。可以优先保障可恢复性和故障报警，但不为了无人值守偏好而牺牲订单唯一性。远端研究服务仍可运行，不等于获得交易执行权。
9. **工程克制：** M0 仅验证 paper-only 单实例/持久状态/模拟重启的关键路径，不接券商，不实现备机编排、分布式租约、云端数据库集群或全套灾难恢复平台。

## 风险导向验收（分阶段）

- 单主机重复启动交易核心：第二实例不得获得执行权；生产迁移时不能出现新旧主机同时可下单。
- 模拟提交过程中掉电，恢复后不能因为本地缺少确认就重复执行同一订单；真实券商环境下需要权威订单状态核对。
- 已触发的亏损熔断、Owner 禁令和账户不确定性在重启后保留。
- 券商现金/持仓/订单和本地账本不一致，禁止新风险并报告原因。
- 状态/备份损坏或不可核实，不能用空账本或旧信号继续交易。

> 本 ADR 是后续实现的架构规则；当前仓库仍为 M0 骨架，没有真实交易执行和券商对账能力。
